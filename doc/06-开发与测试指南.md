# 开发与测试指南

本文面向参与代码开发的团队成员，说明模块边界、接口变更、测试方式和协作规范。

## 1. 仓库结构

```text
aeromind_ws/
├── src/
│   ├── aeromind_interfaces/       公共协议
│   ├── aeromind_bridge/           AirSim/PX4 数据桥
│   ├── aeromind_perception/       图像、检测和 VLM
│   ├── aeromind_autonomy/         地图、重规划和轨迹
│   ├── aeromind_control/          PX4 控制和轨迹跟踪
│   ├── aeromind_agent/            ROS 任务执行
│   ├── aeromind_agent_gateway/    会话、模型、确认和 Workflow
│   ├── aeromind_web/              ROS Web 网关
│   ├── aeromind_bringup/          Launch 和 RViz
│   └── aeromind_teleop/           键盘控制
├── web/ground_station/            独立前端
├── doc/                            项目文档
└── missions/                       运行时任务产物
```

`build/`、`install/`、`log/` 是 colcon 生成目录，不应手工修改。代码修改必须发生在 `src/` 或 `web/`。

## 2. 模块所有权建议

| 方向 | 主要目录 | 职责 |
|---|---|---|
| 平台与接口 | `aeromind_interfaces`、`bringup` | 协议、Launch、配置和集成基线 |
| 数据桥接 | `aeromind_bridge` | AirSim/PX4、坐标转换、TF、QoS |
| 感知 | `aeromind_perception` | 图像、深度、YOLO、VLM 和产物 |
| 自主规划 | `aeromind_autonomy`、`planning` | 地图、避障、轨迹和 Action |
| 飞行控制 | `aeromind_control` | PX4 命令、Offboard、跟踪和安全互斥 |
| 智能任务 | `aeromind_agent`、`agent_gateway` | Runtime、Skills、Workflow、确认和记忆 |
| 地面站 | `aeromind_web`、`web/ground_station` | HTTP/WebSocket、交互和可视化 |
| 测试集成 | 跨包 | rosbag、场景回归、性能和真机流程 |

每个模块应提供清晰接口和独立测试，避免所有人同时修改 Agent 或 Launch 文件。

## 3. 接口变更流程

公共接口位于 `aeromind_interfaces`：

```text
msg/       持续状态与数据
srv/       短时请求/响应
action/    长任务、反馈、取消和结果
```

修改流程：

1. 先写清生产者、消费者、单位、坐标系和时间语义。
2. 修改 `msg/srv/action` 和 `CMakeLists.txt`。
3. 使用 `--packages-up-to` 重建所有依赖包。
4. 重新 source `install/setup.bash`。
5. 更新单元测试、Launch 和对应文档。
6. 用 `ros2 interface show` 验证安装后的接口。

不要用字符串 JSON 替代本应强类型化的关键控制接口。

## 4. ROS 节点开发规范

- 参数必须通过 ROS Parameter 或配置文件暴露，不在代码中散落硬编码。
- Topic/Service/Action 名称集中定义并保持向后兼容。
- 图像和点云使用标准 ROS 消息，不伪造 encoding、step 或 frame。
- 所有位姿和速度明确 frame、ENU/NED、米/秒和弧度单位。
- 长任务使用 Action 或异步状态机，不用阻塞 Service 等待物理完成。
- 传感器回调不得执行长时间网络请求；VLM 等调用应异步处理。
- 回调异常必须被隔离，单帧失败不能让整个节点退出。
- 发布频率、QoS、时间戳和超时应有日志和诊断信息。

## 5. Agent 与 Skill 开发规范

- 模型工具仅暴露经过审查的能力，不提供任意 Bash 或 ROS 发布入口。
- 每个动作定义 JSON Schema、风险等级和确认策略。
- 确认后使用持久化的原始结构化动作，不重新解析用户文本。
- Skill 文档不能声明代码不存在的能力。
- Workflow 每一步都要有完成条件、超时、重试和失败策略。
- 模型输出、工具事实和系统推断在报告中分开记录。
- 新技能应通过插件注册，不把所有意图继续堆进单个规则文件。

## 6. 前端开发规范

- 前端只访问 HTTP/WebSocket 网关，不直接依赖 `rclpy`。
- 状态必须带时间戳，并明确显示离线、过期和未知。
- 服务“已受理”和物理动作“已完成”使用不同状态。
- 检测框、VLM 结论和任务进度必须有过期清理。
- 长列表和对话区必须独立滚动，不能挤压关键飞行状态。
- 高风险确认显示动作、参数、风险、有效期和来源。
- 不在浏览器保存长期 API Key。

## 7. 构建与静态检查

```bash
cd ~/aeromind_ws
source /opt/ros/humble/setup.bash

colcon build --symlink-install
source install/setup.bash
colcon test-result --verbose
```

Python 基础检查：

```bash
python3 -m compileall \
  src/aeromind_agent_gateway/aeromind_agent_gateway \
  src/aeromind_autonomy/aeromind_autonomy \
  src/aeromind_control/aeromind_control
```

## 8. 单元测试

项目环境存在第三方 pytest 插件版本冲突时，可关闭自动加载：

```bash
cd ~/aeromind_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest \
  src/aeromind_agent_gateway/test \
  src/aeromind_autonomy/test \
  src/aeromind_control/test -q
```

重点测试范围：

- 参数解析和能力 Schema。
- 确认过期、越权、幂等和意图一致性。
- Workflow 依赖、条件、暂停、取消、重试和中断恢复。
- ENU/NED、机体系/世界系和航点 frame。
- Minimum Snap 连续性、限幅和局部重规划拼接。
- Control 起飞/降落/轨迹互斥和优先级。

## 9. ROS 集成检查

```bash
ros2 node list
ros2 topic list
ros2 service list
ros2 action list
ros2 topic info /sensor/odometry -v
ros2 topic info /autonomy/trajectory -v
ros2 action info /autonomy/follow_waypoints
```

集成测试至少覆盖：

1. 系统启动和节点就绪。
2. 解锁、起飞、悬停、降落、RTL。
3. 单目标和多航点任务。
4. 中途取消、传感器超时和任务阻塞。
5. 相机、截图、YOLO、VLM 降级。
6. Web 刷新、断线重连、确认恢复和日志一致性。

## 10. 场景回归

单元测试无法证明避障有效。应建立固定 AirSim 场景和 ROS Bag：

| 场景 | 验收点 |
|---|---|
| 空旷直线 | 速度平滑、无误避障、到达误差 |
| 单棵树 | 能提前发现并绕行，不触碰安全半径 |
| 窄通道 | 正确判断可通行或安全终止 |
| 动态人员 | 检测、悬停、重规划与超时 |
| 定位跳变 | 清图、拒绝轨迹、进入安全状态 |
| 深度中断 | `SENSOR_WAIT`，不继续盲飞 |
| Workflow 中断 | 正确失败/取消，不重复执行动作 |

记录成功率、最小障碍距离、路径长度、规划耗时、控制误差和任务完成时间。

## 11. Git 协作

- `main` 或稳定分支只接收经过测试的集成提交。
- 功能分支按模块命名，例如 `feature/autonomy-replan`。
- 提交只包含一个可解释主题，不混入运行产物。
- 不提交 API Key、数据库、ROS 日志、截图缓存和模型大文件。
- 接口变更必须通知所有消费者，并在同一 PR/提交中更新文档。
- 合并前运行 `git diff --check`、相关测试和最小仿真回归。

## 12. 完成定义

一个功能“完成”至少意味着：

1. 代码真实调用底层能力，不只是界面占位或模型文本。
2. 正常、失败、超时和取消路径都有明确终态。
3. 有单元测试或可重复集成测试。
4. 日志能解释失败原因。
5. Web、ROS 和任务状态对同一结果保持一致。
6. 对应专题文档已更新。
