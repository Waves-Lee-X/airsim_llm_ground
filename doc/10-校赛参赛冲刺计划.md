# 7 月 30 日校赛参赛冲刺计划

> 当前日期：2026-07-16  
> 校赛提交截止：2026-07-30  
> 目标：在两周内形成一套稳定可演示、有量化指标、有创新论证、材料完整的参赛作品。

## 1. 冲刺原则

当前项目已经有足够多的功能，校赛前不应继续扩张技术边界。冲刺阶段只做四件事：

1. 冻结并稳定一条端到端演示链。
2. 用对比实验量化大模型带来的提升。
3. 让界面和报告展示模型使用了哪些实时证据。
4. 按比赛模板完成简介、项目文档、五分钟视频和辅助材料。

校赛版本统一称为“参赛基线版本”。除阻塞演示和指标采集的问题外，不再修改底层接口。

## 2. 参赛版本的核心故事

项目要回答的不是“无人机能不能起飞”，而是：

> 如何让大模型理解开放任务、融合无人机多模态状态、动态组合任务流程，同时避免模型幻觉直接进入飞行控制链？

参赛版本的完整回答是：

```text
自然语言任务
→ 混合路由与 LLM 规划
→ Capability/Skill/Workflow 约束
→ 飞控与多模态证据检查
→ 高风险人工确认
→ ROS 2/PX4 确定性执行
→ 遥测验证物理完成
→ 截图、日志和报告归档
```

## 3. 必须完成的系统升级

### 3.1 P0：冻结稳定演示闭环

正式演示只保留以下主任务：

```text
检查当前无人机状态和前方环境，若满足条件则起飞到 10 米，
向前飞行 10 米，到达后悬停拍照，分析当前画面，
返回本轮起飞位置并生成任务报告，最后降落。
```

必须达到：

- 连续执行 10 次，至少 9 次成功。
- 每一步都有唯一终态：成功、失败、取消或超时。
- 服务“已受理”与物理“已完成”严格区分。
- 传感器或遥测过期后 2.5 秒内显示失联，不使用历史值继续判断。
- VLM 失败时自动降级，不导致 ROS 节点崩溃。
- 截图、模型分析、工具调用和任务报告可以关联到同一个 Mission ID。

2026-07-24 已补齐三项 P0 终态修复：

- `perception_node` 使用独立的传感器、拍照和 VLM 回调组，并由三线程执行器调度。VLM 网络推理期间 RGB、深度、CameraInfo、LiDAR 和 YOLO 订阅不得因同一节点阻塞而变为 `STALE`。
- `/control/drone_state` 增加 PX4 接地检测状态。降落步骤只有在 `/fmu/out/vehicle_land_detected` 确认接地、速度稳定且飞控已加锁后才记为物理完成；不再使用相对高度小于固定阈值作为 PX4 降落完成依据。
- 固定主链在 Workflow 启动时记录实时 `odom` 起点。任务结束前通过现有自主规划返回该点上方，水平误差不超过 1 米才允许继续降落，避免每轮在前飞终点垂直降落而累计平移测试原点。
- `DroneState` 增加 PX4 `pre_flight_checks_pass` 映射。安全检查、解锁服务和起飞服务在飞控预检失败时立即拒绝任务，不再把“指令已发送”误报为已解锁，也不再等待 120 秒后才发现起飞失败。

10 次验收中的每一次必须从地面、未解锁状态开始。若 Workflow 中
`takeoff` 因 `if_not_airborne` 被跳过，该次只能作为空中任务链测试，
不能计入完整主链成功次数。

校赛视频暂不使用 RTL 收尾。当前 AirSim-PX4 链路曾在 RTL 过程中出现 `Broken pipe`。参赛主链统一采用“记录任务起点 → Offboard 自主回程 → 水平误差校验 → PX4 原生降落”，回程失败时保持悬停并将该轮记为失败。

### 3.2 P0：增加参赛评测工具

新增离线任务评测入口，输入 JSONL 测试集并输出 CSV/JSON 报告。每条样本至少包含：

```json
{
  "input": "起飞到10米",
  "expected_intent": "takeoff",
  "expected_args": {"altitude": 10.0},
  "expected_confirm": true,
  "expected_tools": ["takeoff"]
}
```

自动统计：

- 意图准确率。
- 参数准确率。
- 工具选择准确率。
- Workflow 步骤正确率。
- 高风险确认召回率。
- 非法指令拦截率。
- 平均响应时延和 P95 时延。
- Token 用量与单次调用估算成本。

校赛阶段任务集建议先完成 80 条：

| 类别 | 数量 |
|---|---:|
| 状态与感知查询 | 15 |
| 明确飞行动作及同义表达 | 20 |
| 多步骤组合任务 | 20 |
| 参数边界与歧义表达 | 15 |
| 未注册、危险或恶意任务 | 10 |

正式初赛前再扩展到 120 条以上。

当前已提供第一版 80 条数据集和离线评测命令：

```bash
cd ~/aeromind_ws
source /opt/ros/humble/setup.bash
source install/setup.bash

# 规则基线：不联网、不连接 ROS、不产生模型费用
ros2 run aeromind_agent_gateway agent_evaluate \
  --dataset evaluation/agent_tasks_v1.jsonl \
  --mode rules \
  --output /tmp/rules.json \
  --csv /tmp/rules.csv \
  --markdown /tmp/rules.md
```

模型评测模式：

```bash
source ~/.config/aeromind/env

# 纯 LLM：不给模型系统能力目录
ros2 run aeromind_agent_gateway agent_evaluate \
  --dataset evaluation/agent_tasks_v1.jsonl \
  --mode llm_free --provider deepseek --model deepseek-chat \
  --output /tmp/llm-free.json

# LLM + Capability/Skill Schema
ros2 run aeromind_agent_gateway agent_evaluate \
  --dataset evaluation/agent_tasks_v1.jsonl \
  --mode llm_schema --provider deepseek --model deepseek-chat \
  --output /tmp/llm-schema.json

# 规则优先，未覆盖任务交给 Schema LLM
ros2 run aeromind_agent_gateway agent_evaluate \
  --dataset evaluation/agent_tasks_v1.jsonl \
  --mode hybrid --provider deepseek --model deepseek-chat \
  --output /tmp/hybrid.json
```

可先增加 `--limit 5` 做小规模联网验证。模型模式会把测试文本和能力目录发送给配置的第三方模型服务，并产生 Token 消耗；评测器只要求模型生成 JSON 计划，不注册 ROS 工具、不创建确认请求，也不会控制无人机。

第一份规则基线见 [规则路由基线报告](../evaluation/rules-baseline.md)。

### 3.4 P0：证据化 Agent 输出

界面和任务报告需要明确区分：

- **传感器事实**：飞控模式、高度、深度、点云、检测结果及采集时间。
- **模型推断**：画面语义、风险解释和任务分解。
- **执行动作**：调用的 Capability、参数、确认编号和 ROS 接口。
- **物理结果**：高度到达、模式变化、截图文件和落地加锁。

建议每条关键事实包含 `source`、`timestamp/age` 和 `fresh`。评委应能看出模型使用了实时数据，而不是引用历史对话编造结论。

第一版证据链已经接入 Agent Gateway 与 Web 控制台：

| 证据 ID | 类型 | 数据来源 | 主要内容 |
|---|---|---|---|
| `flight_state` | 传感器事实 | `/control/drone_state` | 解锁、模式、EKF 与数据时效 |
| `odometry` | 传感器事实 | `/sensor/odometry` | 位置、速度与数据时效 |
| `autonomy` | 系统事实 | `/autonomy/status` | 避障状态、策略、最近障碍物 |
| `detections` | 模型推断 | `/perception/detections` | YOLO 类别、数量与推断时效 |
| `image_analysis` | 模型推断 | `/perception/analyze_image` | VLM 场景分析、模型来源与结果状态 |

ROS 读取工具、安全检查、感知检查和任务物理完成验证均返回统一证据记录。Web 的工具调用区会展示“实时/过期”“ROS 事实/模型推断”、来源话题、数据年龄和摘要。任务报告沿用同一快照结构，便于后续按 Mission ID 做审计和实验统计。

这一实现不代表模型结论一定正确：`fresh=true` 只说明数据在允许时间窗口内，VLM/YOLO 结果仍需通过固定数据集统计准确率和幻觉率。

### 3.5 P1：视觉能力形成最小指标

校赛不必训练新模型，但需要建立 30～50 张固定图像的小型评测集：

- 有人/无人。
- 有车/无车。
- 空旷/近距离障碍。
- 正常光照/低照度。
- 模糊或信息不足画面。

YOLO 统计目标分类正确率、漏检率和平均延迟；VLM 统计场景描述正确率、风险判断正确率、幻觉率和平均延迟。另选 5 个案例说明 YOLO 与 VLM 的分工。

不要用 VLM 文本代替精确测距。距离事实继续来自深度和点云。

### 3.6 P1：一键启动与演示检查

提供一个演示启动入口，至少完成：

- 加载统一环境变量。
- 启动 ROS/PX4 业务节点和 Web/Gateway。
- 检查 8080、8090、DDS Agent 和关键 ROS Topic。
- 输出 RGB、Depth、Odometry、DroneState、VLM/LLM 是否就绪。
- 不在终端打印 API Key、飞书 Secret 和完整 Open ID。

PX4 和 AirSim 可以保留独立启动，但其余 ROS/Web 进程应尽量由 Launch 或脚本统一管理。

当前已提供一个演示 Launch 和两个参赛辅助命令：

```bash
# PX4、DDS Agent、AirSim 就绪后，一条命令启动 ROS/Web/Gateway
ros2 launch aeromind_bringup aeromind_demo.launch.py \
  yolo_enabled:=true vlm_enabled:=true \
  agent_provider:=deepseek agent_model:=deepseek-chat

# 演示前只读预检，并自动保存 JSON 证据
ros2 run aeromind_bringup aeromind_demo_check --require-yolo --require-vlm

# 汇总最近 24 小时中最近 10 个 Workflow，执行 10 次/90% 验收门禁
ros2 run aeromind_bringup aeromind_mission_metrics \
  --since-hours 24 \
  --action workflow \
  --latest 10 \
  --expected-runs 10 \
  --target-success-rate 0.9 \
  --require-takeoff-completed \
  --require-return-to-start \
  --strict \
  --prefix school-demo-10-runs
```

预检覆盖 8080/8090、模型环境、关键 ROS Topic、遥测新鲜度、RGB/深度/点云和控制服务，并隐藏所有凭据值。指标工具统一读取 Gateway SQLite、事件链和 ROS Mission 文件，统计成功率、物理完成率、确认/执行/验证耗时、失败步骤、事件链覆盖率及重复终态事件。

`--strict` 在样本不足、成功率或物理完成率低于 90%、事件链缺失、出现重复终态时返回退出码 2。它是只读工具，不会自动起飞或连续发送任务。10 次任务必须由操作员逐次确认，并在上一轮达到唯一终态后再执行下一轮。

每轮还必须检查：

- `takeoff` 为完成而不是跳过。
- `return-to-start` 为完成，`horizontal_error_m <= 1.0`。
- `land` 最终由接地检测、低速度和加锁共同确认。
- 下一轮开始前仍处于同一测试区域；若要比较严格的绝对轨迹误差，应在每轮后重置 AirSim/PX4 到同一初始位姿，不能把自动回程误差当作仿真重置。

如 24 小时内还有其他 Workflow，可给固定主链统一命名，并增加筛选：

```bash
--title-contains "校赛演示主链"
```

最终证据保存在 `missions/contest/school-demo-10-runs.json`、`.csv` 和 `.md`。剩余工作是用同一 AirSim 场景、同一任务文本、同一模型参数真实执行 10 次主任务，而不是继续修改统计口径。

中途查看进度时不要设置 10 次严格门禁，可缩短时间窗口并只读汇总：

```bash
ros2 run aeromind_bringup aeromind_mission_metrics \
  --since-hours 2 \
  --action workflow \
  --title-contains "校赛演示主链" \
  --prefix school-demo-progress
```

只有完成 10 轮后才使用 `--expected-runs 10 --strict`。正式命令必须同时带
`--require-takeoff-completed` 和 `--require-return-to-start`，否则“空中开始导致
起飞跳过”或“未回到任务起点”的旧记录仍可能被普通成功率统计为完成。

若 PX4 出现 `Preflight Fail: High Accelerometer Bias`：

1. 立即停止继续创建任务，该轮如实记为失败。
2. 重启 PX4 SITL 并将 AirSim 场景恢复到同一初始位姿，不通过关闭预检参数绕过。
3. 等待 `/fmu/out/vehicle_status` 的 `pre_flight_checks_pass: true`。
4. 确认 `/control/drone_state` 中 `preflight_valid: true`、
   `preflight_ok: true`、`armed: false` 后再开始下一轮。

## 4. 校赛前不要做的升级

以下工作价值很高，但不适合塞进两周冲刺：

- 接入真实 VIO/SLAM 并重做标定。
- 替换成熟 ESDF 后端。
- 新增 MPC 并作为默认控制器。
- 从零重做全局/局部规划器。
- 真机首次试飞或复杂树林绕障。
- VLA 直接控制飞行。
- 大规模训练或微调视觉模型。
- 再设计一套新的 Web 技术栈。

这些内容写入升级路线，作为项目延展性和研究计划，不作为校赛交付承诺。
