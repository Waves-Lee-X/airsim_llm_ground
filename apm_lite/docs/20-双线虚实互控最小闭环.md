# 双线虚实互控最小闭环

本实现给「翼策·平行域」提供一条可复现的最小闭环，同时覆盖 PX4 和
ArduPilot/ArduCopter。它把四个 MAVLink UDP 端点放在同一个常驻 Python
桥接进程内：

| 线 | 实机替身（Gazebo + SITL） | 孪生侧（AirSim + SITL） | vehicle_id |
|---|---|---|---:|
| PX4 | `udpin:0.0.0.0:14540` | `udpin:0.0.0.0:14541` | 1 |
| APM | `udpin:0.0.0.0:14550` | `udpin:0.0.0.0:14551` | 2 |

桥接器契约只表达任务级动作：`takeoff`、`waypoint`、`land`、`rtl`；live 配置的能力
白名单默认只授权前三者，RTL 映射存在于适配器但默认不授权。任务契约没有姿态、
角速度、推力或电机字段，因此模型或上层 Agent 没有直接进入飞控实时控制环的接口。

## 代码边界

统一核心位于 `src/aeromind_apm_lite/ground/parallel_domain/core.py`，负责：

- `TwinState` 生成和 `planned/predicted/observed` 轨迹证据；
- WGS84/LOCAL_NED 到统一 `map` 坐标的映射；
- 能力白名单、飞行高度/速度/距离边界；
- 预测完成后的人工确认请求、任务哈希和证据哈希；
- 实端遥测新鲜度、链路、健康和 GPS 门禁；
- 原子状态文件和追加式审计日志。

飞控差异只在 `adapters/px4.py` 和 `adapters/ardupilot.py`：

- PX4 任务使用 `OFFBOARD`，由适配器先发送位置型
  `SET_POSITION_TARGET_LOCAL_NED` setpoint 流，再 ARM 和切换模式；落地/返航只
  映射为 `AUTO.LAND`/`AUTO.RTL`。不上传 `MISSION_*`，也不发送姿态、角速度、推力
  或执行器量。
- ArduPilot 任务使用 `GUIDED`，起飞用 `MAV_CMD_NAV_TAKEOFF`，航点用位置型
  `SET_POSITION_TARGET_GLOBAL_INT`，落地/返航映射为 `LAND`/`RTL`。
- 两个适配器各自定义模式名和命令编号。

核心不判断飞控类型，也不拼接模式字符串；MAVLink dialect (`common` 或
`ardupilotmega`) 由端点配置传给 `adapters/io.py` 的单所有者接口。

## 两条数据流

1. **实控虚（real -> virtual）**：桥接器接收 real 端的 GPS、姿态、心跳模式、
   任务序号和健康字段。只有一条新的 `GLOBAL_POSITION_INT` 才能形成候选位置样本；
   心跳、GPS 状态或姿态消息只能更新健康缓存，不能复用旧位置制造新 observed。
   健康候选统一转换到 `map` 后写入 `TwinStateSet.observed` 和追加式回放日志。
2. **虚控实（virtual -> real）**：计划先由 virtual 端适配器转换并执行，virtual
   遥测生成 `TwinState(source=predicted)` 及 `planned/predicted` 证据。只有
   能力/参数门禁通过、预测证据已落盘、操作员用完整任务摘要确认且 real 端遥测
   新鲜健康时，桥接器才把同一高层计划上传给 real 端并记录 `observed`。

`predicted` 和 `observed` 永远使用不同来源、不同状态槽和不同证据文件；更新任一槽
都不会覆盖另一槽。

PX4 virtual 的 predicted 位置源固定为 `LOCAL_POSITION_NED`。ArduCopter AirSim 同时
发布 local/global，但其 local 原点与配置的 WGS84 home 不等价，因此 APM virtual 固定
只接受 GPS fix >= 3 且非零填充的 `GLOBAL_POSITION_INT`。单次 predicted 证据禁止混合
两个位置源。

## 统一表示与双端时间

公共 `TwinState` 契约包含 `twin_id`、`vehicle_id`、`line=px4|apm`、
`source=sim|real|planned|predicted|observed`、frame、position、attitude、mode、
task phase、sim time、UTC wall time、confidence 和 fidelity。为兼容已有 M1 证据，
`position_m/mission_phase/sampled_at_utc` 保留并与新字段做一致性校验。

每条桥接状态同时记录四个边界字段：`received_monotonic_s`、
`received_wall_time`、`mirrored_monotonic_s`、`mirrored_wall_time`，另保留飞控消息的
`sim_time`（来自 MAVLink `time_boot_ms`，消息不携带时为 null）。monotonic 用于本进程
顺序和延迟，UTC wall clock 用于跨进程及跨线审计，sim time 只用于单线仿真时间轴；
三者不得互相替代。APM 可按 `SITL_SPEEDUP=10` 前进，桥只保证该线 sim time 在飞控
重启归零后仍不倒退，不拿它与 PX4 排序。轨迹采样也保存同样的接收/镜像时刻。

`TwinStateSet` 为 planned、predicted、observed 使用三个独立槽位，更新 predicted
不会改写 observed。该约束属于表示/存储边界，不依赖 PX4 或 ArduPilot 适配器。

## 安装和配置

```bash
cd ~/aeromind_ws/apm_lite
python3 -m pip install -e '.[ground,dev]'
```

默认配置是 `configs/parallel_domain/bridge.yaml`，其中的
`configs/parallel_domain/demo-georeference.yaml` 是**完整但 draft 的演示标定**。
它只用于 SITL 重放和坐标转换测试，证据会保持 `preview_only=true`；外场前必须换成
测绘后的新 `calibration_id`，不能把这个坐标当成真实场地精度结论。

## Live 新鲜度与回放

默认配置 `observation_only: true`。此模式不扫描任务和审批 spool，也不会调用任一
适配器的 `execute()`；本阶段只观察，不下发任务、模式、姿态或电机控制。

real 镜像状态按以下顺序变化：

```text
waiting -> fresh -> stale -> recovering -> fresh
```

- 心跳超时、GPS fix 低于策略阈值、GPS 状态过期、链路异常或位置遥测静默超过
  `telemetry_stale_after_s` 都会进入 `stale`；
- `stale` 和 `recovering` 不更新 observed、不追加轨迹，也不移动最后位置；
- 默认连续 `recovery_samples=2` 条健康新位置样本后才恢复 `fresh`；
- I/O 异常或 MAVLink 静默会关闭 socket 并自动重连。新连接代次清空位置、GPS、
  姿态、模式和任务阶段缓存，`source_sequence` 在进程内连续；UDP 已丢包不能补回，
  桥的保证是不重复、不伪造、不用旧值续命。

常驻状态与回放路径：

```text
.runtime/parallel-domain/
  twin/<line>/real.json          # 最近一条已镜像的 observed 遥测记录
  twin/<line>/virtual.json       # 最近一条 predicted 遥测记录
  twin/<line>/state-set.json     # planned/predicted/observed 独立槽
  twin/<line>/real-status.json   # waiting/fresh/stale/recovering 与原因
  replay/<line>/observed.jsonl   # 可回放 map/observed 轨迹
  audit/events.jsonl             # 拒绝、状态切换和映射审计
```

每条 `observed.jsonl` 顶层包含 vehicle/line/source/frame、wall/sim/monotonic 时间、
标定 ID、SHA-256、`calibration_status` 和 `preview_only`。单线内 sequence 连续，
跨线合并只按 wall time；draft 标定的记录强制保持 `preview_only=true`。

## 离线 live 验收（不启动飞控）

该验收使用确定性的 fake FCU，只验证只读实控虚链路和拒绝路径：

```bash
cd ~/aeromind_ws/apm_lite
PYTHONPATH=src python3 tools/accept_parallel_domain.py \
  --output .runtime/parallel-domain/acceptance.json
```

通过标准：PX4 和 APM 两条线都完成 heartbeat/GPS/link/10 秒静默注入，出现
`stale -> recovering -> fresh`，回放 sequence 与三套时间不倒退，同一 GPS 的 map
结果一致，且 `no_control_dispatched=true`。脚本使用 `surveyed` 验收标定；仓库里的
demo draft 标定仍只能用于预览，不能作为验收证据。

也可以运行测试加验收包装脚本：

```bash
deploy/sim/accept-parallel-domain.sh
```

## SITL 联调顺序

桥接器不替代 Gazebo、PX4、AirSim 或 ArduPilot 的启动器，因为不同版本的启动参数、
模型和 AirSim 插件路径不同。复现时只需把四个飞控进程的 MAVLink 输出配置为上表
端点，并保证系统号分别为 1 和 2；在桥接器启动前，推荐先用飞控自带 console 验证
模式和 Home 已就绪。

典型 ArduCopter SITL 输出配置（只用于启动端点，不是桥接控制命令）：

```bash
sim_vehicle.py -v ArduCopter -I20 --sysid 2 --out=udp:127.0.0.1:14550
sim_vehicle.py -v ArduCopter -I21 --sysid 2 --out=udp:127.0.0.1:14551
```

四个 SITL 输出就绪、桥接器尚未绑定端口时，可以先做只读心跳检查：

```bash
deploy/sim/probe-parallel-domain.sh
```

该检查不发送任务、解锁或模式命令；它只验收四个端口收到的 heartbeat 的系统号是否
分别与配置中的 `target_system` 一致。

PX4/Gazebo 和 PX4/AirSim 由 `deploy/parallel_domain/start_all.sh` 编排；关键是分别
把两个实例的 MAVLink 输出送到 14540、14541，并保持 PX4 `SYSID_THISMAV=1`。
AirSim 侧只承载虚拟演练，Gazebo/原生 SITL 侧只承载实机替身，不能把仿真画面描述成
外场飞行。Windows 上用 `start_all.ps1` 时，两个 UE 进程分别使用生成的
`%LOCALAPPDATA%\\Aeromind\\parallel-domain\\airsim\\px4|apm\\settings.json`，并以
AirSim 1.8.1 支持的 `-settings=<绝对路径>` 启动；不会写入或共享
`Documents\\AirSim\\settings.json`。两个 profile 的 RPC 固定为 `41451/41452`，脚本
还会校验默认 settings 的启动前后 SHA-256，防止静默回退到单一配置。

启动常驻桥：

```bash
deploy/sim/start-parallel-domain.sh
```

启动后它会持续订阅四个端点。默认只读模式写入以下状态和证据：

```text
.runtime/parallel-domain/
  twin/<line>/real.json
  twin/<line>/virtual.json
  twin/<line>/state-set.json
  twin/<line>/real-status.json
  replay/<line>/observed.jsonl
  audit/events.jsonl
```

## 任务和人工确认

以下是 live 虚控实接口；默认 `observation_only=true` 时 spool 不会被处理。必须使用
`bridge-control.yaml`，该配置显式关闭 observation-only 并保留同一套安全门禁。

提交虚拟演练计划：

```bash
PYTHONPATH=src python3 -m aeromind_apm_lite.ground.parallel_domain.cli submit \
  --config configs/parallel_domain/bridge-control.yaml \
  --mission configs/parallel_domain/missions/px4-live.json
```

把 `px4-live.json` 换成 `apm-live.json` 即可走 APM 线。桥接器收到计划后先只向
对应 virtual 端发送任务。任务完成并形成当前 AirSim 预测证据后，会生成
`approval_requests/<mission_id>.json`，其中包含 `mission_hash` 和
`predicted_evidence_hash`。确认摘要是三者的 SHA-256：

```text
mission_id + mission_hash + predicted_evidence_hash
```

显式输入操作员、任务摘要和确认摘要，才会放入真实执行队列：

```bash
PYTHONPATH=src python3 -m aeromind_apm_lite.ground.parallel_domain.cli approve \
  --config configs/parallel_domain/bridge-control.yaml \
  --mission-id <MISSION_UUID> \
  --mission-hash <MISSION_HASH> \
  --operator operator-01 \
  --digest <CONFIRMATION_DIGEST>
```

桥接器会重新检查 real 遥测的新鲜度、FCU 健康和 GPS fix type；任一条件不满足，
任务保持拒绝状态，且不会发送任何 real MAVLink 命令。成功后 PX4 只走 OFFBOARD
位置 setpoint，APM 只走 GUIDED 起飞/全局位置 setpoint；状态可随时查看：

```bash
PYTHONPATH=src python3 -m aeromind_apm_lite.ground.parallel_domain.cli status \
  --config configs/parallel_domain/bridge-control.yaml
```

## 验收证据和边界

- `planned` 是任务目标折线；`predicted` 必须来自当前 AirSim/SITL virtual 遥测；`observed`
  来自 Gazebo/SITL real 遥测。
- 每个证据文件包含任务 ID、vehicle ID、标定 ID/hash、时间序列、GPS 质量和来源，
  并通过现有 `TrajectoryEvidenceStore` 原子保存。
- 任务摘要、预测证据摘要和操作员确认记录都会进入 `audit/events.jsonl`。
- 该最小闭环不宣称飞控版本、Gazebo 世界、AirSim UE 场景或外场标定已经由仓库统一
  安装；这些版本必须由运行者冻结并写入现场复现记录。提交 live 任务必须使用
  `sitl-georeference.yaml` 的 `parallel-sitl-locked-v1`，draft 标定只能预览。
- 适配器不接收 AI 姿态或电机输出；底层姿态稳定、位置估计、围栏和 failsafe 始终
  由 PX4/ArduPilot 负责。`LiveTrajectoryComparison` 只按 UTC wall time 对齐
  predicted 与 observed，绝不用 APM 的加速 sim time 跨线排序。
- 控制配置中的 `force_arm_for_sitl` 默认关闭，只在本地 SITL 验收 profile 开启，使用
  MAVLink 标准 SITL magic `21196` 绕过 AirSim 传感器预检；它不是外场或真机配置。

阶段四 live 证据完成后执行：

```bash
PYTHONPATH=src python3 tools/accept_parallel_domain.py \
  --live-control-state-directory .runtime/parallel-domain-control \
  --output .runtime/parallel-domain-control/live-control-acceptance.json
```

验收器不会连接或控制飞控；它只读核对两条线的八段事件链、一次性 approval ledger、
predicted/observed evidence、执行语义、wall-time comparison 和阈值结果，同时要求审计中
存在 capability whitelist、TTL 过期和重放拒绝。`apm-denied-rtl.json` 用于越权注入；
TTL 注入可临时将验收配置设为最小 30 秒，完成后恢复 600 秒。比较阈值仍是 SITL
provisional 阈值，不能据此宣称外场精度或真实飞行安全已验收。

## 阶段五：live 异常与人工确认闭环

阶段五的专用验收 profile 是 `configs/parallel_domain/bridge-live-faults.yaml`。它不改变
核心门禁，只把 TTL 收紧为 30 秒并显式允许针对 `gazebo`/`native-sitl` real 端的
SITL-only 故障入口。四个 SITL/UE session 已启动时运行：

```bash
deploy/sim/accept-parallel-domain-live-faults.sh
```

编排脚本只替换地面桥 tmux session，保留四个飞控和两个 UE 世界；结束后恢复
`bridge-control.yaml`（生产 TTL 600 秒）。上一次专用 runtime 会先完整归档到
`.runtime/parallel-domain-live-faults-history/`，避免旧 spool/恢复状态污染新一轮，且不删除
历史失败证据。验收器为 PX4、APM 各生成独立 mission，检查：

- 白名单外 `RTL` 在 rehearsal gate 被拒，审计有 `rehearsal_rejected`、命令和
  `capability_whitelist` 原因；
- 合法任务的 approval TTL 到期后被拒，审计有 `approval_ttl_expired`，没有任何 real
  dispatch；
- 未确认的 `request-dispatch` 先产生
  `real_dispatch_rejected(reason=operator_confirmation_missing)`，之后人工确认、预测
  证据摘要和 real dispatch 才被接受；
- 一次性 `inject-fault --confirm-sitl` 在 live telemetry health gate 将 heartbeat/GPS
  标记为不健康，real observed 停止，随后按适配器映射执行
  `safety_hold -> recovery_land`，健康样本恢复后完成 observed 轨迹。

命令入口示例：

```bash
PYTHONPATH=src python3 -m aeromind_apm_lite.ground.parallel_domain.cli request-dispatch \
  --config configs/parallel_domain/bridge-live-faults.yaml \
  --mission-id <MISSION_UUID> --line px4 --vehicle-id 1

PYTHONPATH=src python3 -m aeromind_apm_lite.ground.parallel_domain.cli inject-fault \
  --config configs/parallel_domain/bridge-live-faults.yaml \
  --mission-id <MISSION_UUID> --line px4 --vehicle-id 1 --confirm-sitl
```

PX4 适配器会根据该固件的 `mode_mapping()` 选择 `AUTO.LOITER/AUTO_LAND` 等别名；
当前 pymavlink PX4 map 广播为 `LOITER`、`LAND`、`RTL` 时，审计中的 `command` 会记录
实际采用的 `SET_MODE:LOITER` 或 `SET_MODE:LAND`，核心仍只看到
`safety_hold`/`recovery_land` 两个任务级动作。若 PX4 重连窗口尚未建立动态 mapping，
适配器使用 PX4 固定主/子模式参数发送 `MAV_CMD_DO_SET_MODE`；这仍是飞行模式命令，
不包含姿态、角速度、推力或电机量。

拒绝、故障注入和安全动作均是结构化 audit 事件，包含 `reason`、`wall_time`、机号、线
和命令；报告位于 `.runtime/parallel-domain-live-faults/`。`heartbeat/GPS loss` 的
`injection_layer` 会明确写为 `live_telemetry_health_gate`，不能把这类测试日志描述成
物理链路故障。stale/recovering 期间最后一条 observed 位置保持不变，sim time 只用于
线内排序，跨线审计和结果比较仍使用 wall time。

## 阶段六：live 证据与标定冻结

证据包由同一任务的 `planned`、AirSim 当前遥测 `predicted` 和 real 遥测 `observed`
组成，全部先转到 `map`。`manifest.json` 包含 mission ID、line、vehicle ID、版本表、
软件树 SHA-256、随机种子、UTC 时间范围、标定 ID/SHA-256、三份原始 evidence hash、
三组 pairwise 误差报告和整体 `content_sha256`。包内 `observed-replay.jsonl` 必须逐条
对得上 observed evidence 的 wall timestamp 和 map 位置。

标定状态只能按以下路径变化：

```text
draft (preview_only=true, acceptance_passed=null)
  -> 实测/独立仿真真值 dataset
  -> 至少 6 样本、3 控制点、outbound+return、真值来源和误差阈值通过
  -> freeze receipt 固定 draft SHA + frozen SHA + dataset/report SHA
  -> surveyed (preview_only=false, acceptance_passed=true)
```

`tools/calibrate_parallel_domain.py freeze` 和 `verify` 实现这条门禁。Gazebo live 用例
使用 `capture-gazebo`：它把 Gazebo ENU 根位姿与最近 GPS-derived observed 按 wall time
配对，保存独立真值、配对偏差和真实误差分布；`--append` 用于不同控制点和返航段，控制点
不足时报告不可用于验收。APM 线可复用仓库中的
`configs/parallel_domain/calibration/apm-sitl-ground-truth-roundtrip.json` 作为确定性
SITL 输入，正式外场仍需替换为独立 `line=apm, vehicle_id=2` live dataset。

一条命令生成包、另一条命令校验包：

```bash
deploy/sim/accept-parallel-domain-live-evidence.sh <MISSION_UUID> px4 .runtime/live-evidence.zip
PYTHONPATH=src python3 tools/package_parallel_domain_live.py verify .runtime/live-evidence.zip
```

正式包会重算 planned-predicted、planned-observed、predicted-observed 的水平/垂直/三维
RMSE、最大误差、P95 和终点误差；即使指标未通过，冻结 receipt、artifact hash 和原始
日志仍必须可校验。材料措辞为“实现往返自洽 1.6e-9 m + live 标定误差实测值”，绝不把
坐标往返自洽写成“0 m 误差”，也不以 draft 标定或模型总结替代原始证据。
